Software Supply Chain Guardian ssc-guardian v1.0.1-reference · source on GitHub
A reference implementation, not a production tool.

The author uses Guardian every day in his own development work, but he publishes it as a reference implementation: a worked example of these defences. Do not rely on it for production work. It comes with no support and no stability promise.

For engineering leaders: a five-minute read

Mitigate software supply chain attacks on your workstation and in GitHub Actions.

Modern software is built upon thousands of open source projects. Programmers download these projects and every update to them. They often accept those updates without a second look. Attackers know this. They steal a project author's password, publish an update with harmful code hidden inside, and wait for it to spread. Guardian stands between the programmer and those updates. It looks for Indicators of Compromise (signs that an attacker has taken over a project), such as malware reports about the project, a known security flaw, code that claims to come from a project but does not, and a version label that someone has moved to point at different code. Guardian reports every sign it finds, blocks the serious ones, and explains each decision in plain words. It also holds each new release for a cooldown, a waiting period you set, which gives security researchers time to find and report an attack.

Guardian protects a developer's Mac and the team's GitHub repositories from poisoned updates. It makes new Python packages and GitHub Actions wait out a holding period, the cooldown. It checks threat feeds and known vulnerabilities, pins Actions to verified commits, and explains every decision.

Guardian runs entirely on your own machine. It has no server, no account and no telemetry, and it sends nothing to its author. Its only network traffic is lookups to five public services, listed below under What Guardian runs and sends. Each lookup names at most the packages and Actions being checked, and Guardian's own requests identify the client only as ssc-guardian. The one exception is ssc-guardian install, which installs packages with the standard pip. Guardian does not change pip: it pins pip to one release and checks pip's wheel against a SHA-256 written in Guardian's code. As it does for everyone, pip tells PyPI your Python version, operating-system version and processor type. A GitHub token is optional; if you give Guardian one, it goes only to GitHub.

Guardian has no dependencies. It uses only Python's standard library, so installing it pulls in no other package that could itself carry poison.

The problem

Yesterday's trusted update can be hostile today.

Teams pull in new code automatically, and attackers use that habit.

A build takes the newest package version on every install, and a CI run takes whatever commit an Action's tag names that day. An attacker who takes over one popular package or one tag runs his code in every project that pulls it in, before anyone has a chance to report it.

One example came in March 2025. The GitHub Action tj-actions/changed-files (CVE-2025-30066: GitHub advisory, NIST record) called reviewdog/action-setup@v1 by its tag (CVE-2025-30154: GitHub advisory, NIST record). The attackers moved that tag, and their code ran inside every workflow that used tj-actions. Both flaws are in CISA's Known Exploited Vulnerabilities catalog (CISA's alert).

What Guardian does

Five jobs, one rule set, one report.

Each job closes one route a poisoned update can take.

Cooldown

Wait before trusting

A new PyPI version or Action commit waits 21 days by default. The wait gives the security community time to find and report a bad release.

Threat feeds

Check what is known

Guardian reads malware reports from OSV, GitHub and PyPI's quarantine, and known flaws from reviewed advisories. It labels a flaw that CISA lists as exploited.

Pinning

Verify every Action

A pin names an Action by its 40-character commit ID (SHA). Guardian accepts a pin only when a lock file, the list of allowed pins, holds it and the commit traces to the publisher.

Explanation

Say why, every time

Each finding names the rule, the place, the evidence, and, where one exists, the command that fixes it. Guardian lists anything it could not check as skipped, never as clean.

Zero dependencies

Add no risk

A supply-chain tool must not become a supply-chain risk. Guardian imports nothing outside Python's standard library. For checked installs it uses the standard pip. Guardian does not change pip: it pins pip to one release and checks pip's wheel against a SHA-256 written in Guardian's code.

How it works: 1

The cooldown buys time for detection.

A new version waits before Guardian will install or pin it, and Guardian checks the threat feeds on every run, during the wait and after it.

How it works: 2

Exact pins and version ranges

Guardian answers one question: which version is safe to take today.

What you ask forWhat Guardian does
install --venv .venv NAME
a loose request		Guardian picks the newest version that passes every rule today (cooldown, malware and vulnerability feeds, deny list) and fits the virtual environment (venv). It tells pip to go no higher, checks every dependency pip resolves as one set, and installs exactly those files, each bound to the SHA-256 that PyPI publishes.
install --venv .venv NAME==VERSION
an exact pin		Guardian checks that version. If the version is too young, compromised, or vulnerable, Guardian refuses it, names the newest version that passes, and prints the command that installs it.
pip install "NAME>=1.2"
a range, with plain pip		ssc-guardian protect writes pip's own cooldown setting into the venv, so pip takes the newest version older than the cooldown; it writes uv's setting into uv's user config when a named path holds it. Plain pip still skips the malware and vulnerability checks; install --venv is the checked path.

install takes only NAME or NAME==VERSION. It refuses web addresses, local paths, editable installs, and requirement-file options before pip resolves anything. Guardian 1.0.1 does not yet check requirements and lock files (pyproject.toml, requirements*.txt, uv.lock); a later release adds them. check --envs checks what a venv actually holds, however it got there.

How it works: 3

A check searches only the paths you name.

It has no default scope and no hidden settings, and it never calls “unknown” safe.

IN

Paths you name

--path for Python environments, --repo for one repository's workflows.

FIND

Environments and workflows

Venvs and Python installations at or under each path; the workflows and the Actions they reach.

APPLY

Every rule

The cooldown, the malware and vulnerability feeds, the pins and lock file, your settings, and your deny list.

REPORT

Findings and skips

Violations, warnings, and notices, with what Guardian checked, what it skipped, and why.

EXIT

One code for the gate

0Every rule met in what was checked.
1At least one violation.
2A check could not finish, or a usage error. Skipped is unknown, not safe.
A failed check never gives 0. A feed that does not answer, a rate limit, or an error inside a check counts as a skip, and the run exits 2.
1 wins over 2. Once Guardian knows of a violation, the result is 1, and the report still lists the unfinished checks.
Warnings and notices never fail a run. Each rule has one fixed level; an exception goes through a recorded override.
Warning signs

Indicators of Compromise Guardian detects

Each rule watches for one sign of a takeover, an impostor, or a known bad release.

Too new to trust
  • cooldown: a version younger than the waiting period.
  • young-repository: an Action repository under 90 days old or under 50 stars. It blocks until a person accepts it.
  • first-use-publisher: a publisher new to this repository, shown with its age, stars, and forks.
Known bad
  • compromise: malware reports from OSV, GitHub, and PyPI's quarantine.
  • known-vulnerability: reviewed advisories, labelled when CISA lists the flaw as exploited.
  • unreleased-pin-advisory and deny-list.
Not who it claims to be
  • impostor-commit: a commit that no publisher tag, branch, or default-branch history reaches, such as code pushed through a fork.
  • unpushed-commit: a commit never seen on a publisher branch.
  • unverified-pin: a pin missing from the lock file.
Changed underneath you
  • moving-reference and nested-moving-reference: a tag or branch that can move to other code.
  • moved-release-tag: a recorded release tag that now names another commit.
Hidden or unverifiable
  • unpinned-image: a Docker image with no digest.
  • nesting-limit and nesting-loop: Actions nested too deep or in a loop.
  • unprotected: no cooldown, or a package index other than PyPI's.
Planned for v1.1
  • A young owner account: an Action whose owner's GitHub account is new.
  • A lookalike name: an Action named one typo, separator, or lookalike letter away from a well-known Action.
  • A new contributor: a pinned commit written by an account new to that repository.
How it works: 4

Six GitHub Actions threats, one design.

A GitHub Action is a reusable step that a CI workflow runs. These six defences stop the attack described above, and attacks like it, in your own repository's workflows.

Moving tag

Every reference must be a 40-character commit SHA. check --repo reports a tag or branch, and pin pins it.

Malicious release

Every new commit has a cooldown. pin records a young commit in the lock file but leaves the workflows alone. Run pin again once the commit is eligible.

Wrong publisher

An Action repository created under 90 days ago, or with under 50 stars, blocks until a person runs acknowledge.

Impostor commit

Guardian accepts a commit only when a publisher tag, branch activity, or default-branch history reaches it.

Nested Action

Guardian reads the references inside a pinned Action at its pinned commit and checks them the same way.

Known vulnerability

Guardian checks every pin against GitHub's reviewed advisories on every run.

How it works: 5

You verify Guardian before you install it.

A security tool is itself a target, so Guardian holds its own release to the same standard. You verify one wheel with no dependencies, so what you verify is all of Guardian's code.

Release workflow

Build

The public repository's workflow builds the wheel with a hash-locked build tool and every Action pinned by SHA.

GitHub and Sigstore

Attest

GitHub attaches an artifact attestation: keyless Sigstore signing, with no named key to steal.

GitHub

Freeze

A published release is immutable: nobody can move its tag or replace its files.

You

Verify

gh attestation verify checks the downloaded wheel against that attestation before anything runs.

Your gate and CI

Pin

A commit gate or CI job pins the wheel's SHA-256 and checks it on every run.

Where it runs

On the developer workstation, at the commit, in CI.

The same rules apply in all three places.

A developer's Mac

  • check examines the Python environments you name.
  • protect writes the installers' own cooldown setting into pip's and uv's configuration files.
  • install --venv checks everything pip would install, then installs exactly those files.
ssc-guardian check --envs --path ~/projects/app/.venv

A commit gate

  • Each repository pins its own Guardian version and wheel SHA-256.
  • Before every commit, the gate checks the hash, then the repository's workflows and lock file.
ssc-guardian check --repo .

CI

  • The same check --repo runs on Linux runners.
  • Only the default branch's overrides count, so a pull request cannot release its own finding.
ssc-guardian check --repo . --json
Agents and people

Built for agents and for people.

One run gives the same findings two ways: JSON that a program can act on safely, and plain text that a person can act on quickly. Where a decision belongs to a person, Guardian keeps it there.

For LLM agents
  • A contract, not screen-scraping. --json prints one object in a versioned format. Its keys are sorted and always present, so an agent never guesses at a missing field.
  • Exit code first. Each of 0, 1, and 2 maps to one next step, and the output never reports an unfinished check as clean.
  • Fixes as exact argument lists. A fix command is a list of arguments, passed one per argument and never joined into a shell string. It is always install, pin, or protect.
  • Clear hand-off flags. requires_person, requires_user_approval, and eligible_on tell the agent when to stop and ask, or when to report a date and wait.
  • Output is data, never instructions. Every value is a fixed name or matches a strict pattern, so a hostile package name cannot plant a prompt in the agent's context.
  • No hidden state. A check searches only the paths its arguments name; no setting or saved state widens it.
  • Ready-made guidance. Guardian's docs give an agent instructions page and, for Claude Code, a CLAUDE.md snippet, permission rules, and an optional hook. Together they steer an agent's package installs to Guardian.
For people
  • A readable report. Each finding gives the rule, the place, the fix command where there is one, and a stable ID to track it.
  • Show before write. Every command that changes something shows the change and asks first.
  • Exceptions belong to people. acknowledge and override add never appear in JSON, refuse --yes and --json, and need a person at a terminal.
  • A second warning for the worst cases. For confirmed malware or an exploited flaw, override add warns again and asks the person to type the advisory ID.
  • Context for judgment. The first use of an Action's publisher shows the repository's age, stars, and forks.
0Report the result, and read the skipped list anyway.
1Run the finding's exact fix command, or hand the finding to a person.
2Stop and report. Never retry in a loop; never call it a pass.

The terminal requirement slows a program down; it does not lock it out. Your agent's permission settings and CI with protected branches are the real enforcement points, and Guardian's docs give a pattern for each.

The API

JSON format 1.0 for programs

Add --json to check, protect, install, or pin. The output is one ASCII object with sorted keys; an empty value is null or [], never missing. Text and JSON come from the same findings.

format_version, tool, command, exit_code
What ran, which version, and the same 0, 1, or 2 that the shell sees.
summary
Counts of violations, warnings, notices, checked items, and skips in and out of scope.
findings[]
Each with id, rule, level, ecosystem, place, item, version, evidence, labels, options, malformed_field, and via.
options[]
The ways out: replace, protect, remove, or exception, with a ready argument list where one applies.
checked[], skipped[], overrides
What Guardian examined, what it did not and why, and which overrides applied or expired.

A finding's id stays the same from run to run: the first 32 hex characters of a SHA-256 over the finding's rule, place, ecosystem, item, version, and related fields. Tickets and dashboards can track it.

What it runs and sends

What Guardian runs and sends

Guardian keeps its own footprint small on purpose. It runs on your machine, has no server or telemetry, and sends only the lookups below.

Guardian runs three programs and no others: its own interpreter; a venv's Python, only inside install --venv (locked down for the check, and in normal mode only after every check passes and you confirm); and gh auth token, only from Homebrew's fixed locations and never through PATH. It reads every other program it finds from disk and never runs it.

On the network, Guardian talks over HTTPS to five services and refuses any other address, a redirect included:

api.github.comapi.osv.devpypi.orgfiles.pythonhosted.orgwww.cisa.gov

Every request is a GET except OSV's batch query. Your GitHub token goes only to api.github.com and never appears on screen, in a log, or in JSON.

Known limitations

Read these before you rely on any result.

  • A reference implementation. Not for production; no support and no stability promise.
  • Runs natively only on macOS. On Linux only check --repo is supported, as in the CI example.
  • Python and GitHub Actions only. Homebrew, npm, and Cargo come later.
  • Only what you name. Guardian does not search the Mac for venvs.
  • Full protection means installing packages through Guardian's command-line interface (ssc-guardian install --venv). Some of Guardian's protections still hold when you run pip or uv directly: pip and uv obey the cooldown that protect sets, and ssc-guardian check still finds a bad package after it is installed.
  • Time, not certainty. The cooldown buys time for detection; it does not guarantee detection.
  • No lock against you. A program or agent that runs as you can edit your Guardian settings, override and lock files, and Guardian's own code; agent permissions and protected-branch CI enforce the rules.
  • CI believes the lock file as written. The lock file (.ssc-guardian.lock) lists the Action versions Guardian has verified and the date each one's cooldown started. CI does not verify them again, so an edit to the file could approve an unverified Action or cut a cooldown short. Review every change to the lock file in a pull request.
  • What an Action brings with it is unchecked. Guardian verifies the commit an Action is pinned to, but not three things the Action's code can bring along: the contents of a Docker image it starts, including any Python packages in it (Guardian checks only that an Action's image is pinned); anything it downloads while it runs; and the npm packages built into a JavaScript Action.
  • Coming in v1.1. Guardian will detect three more Indicators of Compromise: an Action whose owner's GitHub account is new, an Action whose name is one typo or lookalike letter away from a well-known Action, and a pinned commit written by an account new to that repository. The same release adds a repository settings report, guided setup, pre-commit hooks, and checks of dependency files.
Try it

Download, verify, install.

Before you start, you need:

  • macOS
  • Python 3.11 or later (uv supplies it if your Mac has none)
  • uv
  • gh, the GitHub command-line tool. Only step 2, verifying the release, needs it signed in (gh auth login). Downloading works without signing in. Guardian also uses the sign-in, if present, for GitHub's higher request limit.

Install Guardian in its own environment, never in a project's venv.

  1. Download the release.

    gh release download v1.0.1-reference -R thomascburns/ssc-guardian -p 'ssc_guardian-*.whl'

  2. Verify it before anything runs.

    Stop here if this step fails.

    gh attestation verify ssc_guardian-1.0.1-py3-none-any.whl -R thomascburns/ssc-guardian \
  --signer-workflow thomascburns/ssc-guardian/.github/workflows/release.yml \
  --source-ref refs/tags/v1.0.1-reference

  3. Install it in its own environment.

    uv tool install ./ssc_guardian-1.0.1-py3-none-any.whl

  4. Check a project.

    Run this inside a project that has a .venv folder.

    ssc-guardian check --envs --path .venv
